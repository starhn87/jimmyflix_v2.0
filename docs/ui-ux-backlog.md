# UI/UX 개선 백로그

> 이 문서는 전환 전 화면을 기준으로 만든 과제와 수용 기준을 보존한다. 구현 결과는 [개선 작업 진행 기록](improvement-progress.md), 전환 후 설계는 [App Router·Tailwind 전환 기록](app-router-overhaul.md)에서 확인한다.

작성일: 2026-09-10 · 총 28개 항목: P1 8개, P2 18개, P3 2개

> 이 문서는 최초 진단 기준을 보존한다. 이후 구현과 검증 상태는 [개선 작업 진행 기록](improvement-progress.md)에서 관리한다.

이 문서는 저장소의 기존 UI 코드와 구조 분석, 기존 배포본의 제한적인 브라우저 관찰을 바탕으로 정리한 개선 후보다. 현재 작업 범위는 **분석 문서 작성**이며, 애플리케이션 코드 변경·패키지 설치·로컬 서버 기동·수동 배포는 수행하지 않는다. 문서의 커밋·푸시는 저장소 반영 작업으로 구분한다. 구조와 기술 부채의 전체 진단은 [저장소 분석](repository-review.md)을 함께 참고한다.

## 읽는 방법

- **P1**: 핵심 탐색 흐름이 끊기거나 조작·정보 정확성에 영향을 주는 문제. 먼저 개선한다.
- **P2**: 가독성, 화면 구성, 탐색 편의, 로딩 경험의 개선. P1 이후 묶어서 진행한다.
- **P3**: 사용자 요구와 실제 화면 검증을 거쳐 적용 범위를 결정할 제안.
- **코드 확인**: 현재 소스에 해당 구현이 존재하거나 처리가 없는 것을 확인했다. 모든 런타임 증상을 재현했다는 뜻은 아니다.
- **브라우저 관찰**: 2026-09-10 기존 배포본에서 직접 확인한 화면이다. 아래 관찰 범위를 참고하며, 저장소 기준 커밋과 배포본의 일치는 확인하지 않았다.
- **디자인 제안**: 현재 코드를 바탕으로 제안하는 변경 방향이다. 현행 동작을 곧바로 결함으로 단정하지 않는다.
- **실측 필요**: 브라우저·기기·보조 기술·네트워크 조건에서 추가 확인해야 한다. 성능, 대비, 터치 크기, 사용자 선호를 측정한 결과는 없다.

아래 수용 기준은 **향후 구현 완료를 판단할 검증 조건**이며 현재 통과 결과가 아니다. 코드 근거의 줄 번호는 작성 당시 기준이다. Lighthouse 점수, 전환율, 이탈률 및 성능 개선 수치는 측정하지 않았다.

### 브라우저 관찰 범위

[기존 배포본](https://jimmyflix.vercel.app/)을 데스크톱 1280×720 및 모바일 viewport 390×844에서 관찰했다. 실제 터치 기기 검증은 아니다.

- 홈·검색 화면을 확인했다. 모바일에서 `The Lord of the Rings` 검색 시 본문 전체 로딩 화면을 거쳐 결과가 표시되며 검색창과 검색어 표시가 사라졌다.
- 같은 검색 결과의 여러 카드 제목이 `The Lord of the Ri…`로 잘려 구별하기 어려웠다.
- 모바일 `/movies/122` 상세 첫 화면의 대부분이 포스터였고 제목은 화면 하단, 평점·정보는 아래에 있었다.
- 같은 상세의 Trailer 탭 영상 박스는 약 370px 너비에 400px 높이였다. 표시된 영상 제목은 `The Lord of the Rings: The Return of the King | Siege of Gondor Begins | ClipZone: Heroes & Villains`로 장면 클립이었으며 재생하지 않았다.
- `/trend` 기본 Day 화면에서 `Error in Movie Trend`, `Error in TV Show Trend`와 재시도 버튼이 없는 상태를 확인했다. 네트워크 원인은 추적하지 않았으므로 특정 API 원인으로 단정하지 않는다.

이 관찰은 배포본의 제한된 화면 사례다. 키보드·보조 기술·200% 확대·전체 브레이크포인트·느린 네트워크 시뮬레이션·성능 측정은 실시하지 않았다.

## 검색과 결과 탐색

### UX-01 · P1 · 모바일 검색 결과에서도 바로 재검색

- **구분:** 코드 확인 + 브라우저 관찰 + 디자인 제안.
- **현재 문제·사용자 영향:** 검색 후 본문의 검색창은 결과 목록으로 대체되고, 너비 768px 이하에서는 헤더 검색창도 숨겨진다. 결과 화면에서 검색어를 바로 수정할 수 없고, `Search` 내비게이션을 다시 눌러 상태를 초기화해야 한다.
- **제안:** 결과 상단에 검색어가 채워진 검색 폼을 유지한다. 검색어 수정·제출·지우기를 같은 위치에서 제공한다.
- **수용 기준:** 320·375·768px에서 첫 검색 후 내비게이션 이동 없이 다른 검색어를 제출할 수 있다. 입력 폼은 검색 진행 중에도 유지되고, 현재 결과의 검색어를 확인할 수 있다.
- **코드 근거:** [검색 페이지](../pages/search.tsx) 46–66행의 조건부 검색창, [헤더](../components/common/Header.tsx) 20–25행의 검색 초기화 및 149–152행의 검색창 숨김.

### UX-02 · P1 · 검색창의 고정 너비 제거

- **구분:** 코드 확인 + 실측 필요.
- **현재 문제·사용자 영향:** 입력 요소는 600px 고정인데 부모는 기본 500px, 모바일에서는 80%다. 입력 요소가 검색창 테두리 밖까지 차지하는 CSS 구조이며 작은 화면에서 잘림·가로 넘침·버튼 겹침을 확인해야 한다.
- **제안:** 폼 내부를 입력 영역과 제출 버튼의 grid/flex로 구성하고 입력은 남은 너비를 사용한다. 모바일 키보드가 열린 상태에서도 입력·제출 영역을 유지한다.
- **수용 기준:** 320·375·768·1024px 및 200% 확대에서 검색창으로 인한 가로 스크롤이 없고, 긴 검색어와 제출 버튼이 겹치지 않는다. 모바일 키보드 표시 중 제출할 수 있다.
- **코드 근거:** [본문 검색창](../components/SearchBar.tsx) 42–64행의 입력 스타일, 67–78행의 버튼 위치, 85–112행의 부모 너비.

### UX-03 · P1 · 검색어와 결과 상태를 URL에 유지

- **구분:** 코드 확인 + 디자인 제안.
- **현재 문제·사용자 영향:** 검색어와 검색 여부는 Recoil 메모리에만 저장되고 헤더도 `/search`로만 이동한다. 새로고침이나 URL 공유 시 같은 검색 결과를 복원할 수 없으며, 검색어 변경 이력도 URL에 남지 않는다.
- **제안:** `/search?q=...`를 검색 상태의 기준으로 삼는다. 검색 제출은 URL을 갱신하고, 입력 초안과 제출된 검색어를 구분한다.
- **수용 기준:** 검색 URL 새로고침·새 탭 열기·직접 진입 시 같은 검색어와 결과를 표시한다. 검색어 두 개를 차례로 제출한 뒤 뒤로/앞으로 이동하면 URL과 입력·결과가 일치한다. 공백 검색어는 검색하지 않는다.
- **코드 근거:** [검색 페이지](../pages/search.tsx) 14–15·30–32행, [Recoil 상태](../recoil/store.ts) 4–12행, [헤더 검색창](../components/HeaderSearchBar.tsx) 25–28행.

### UX-04 · P2 · 검색 결과 수와 다음 결과 제공

- **구분:** 코드 확인 + 디자인 제안.
- **현재 문제·사용자 영향:** 검색 요청은 `page`를 전달하지 않고 `results` 배열만 반환한다. 결과 화면에는 전체 개수와 추가 페이지 탐색 UI가 없어 사용자가 결과의 범위나 다음 결과 유무를 알 수 없다.
- **제안:** API 응답의 페이지·전체 결과 메타데이터를 유지하고 영화/TV별 결과 수와 `더 보기` 또는 페이지 이동을 제공한다. 사용자가 요청한 시점에 다음 결과를 불러오는 방식을 우선 검토한다.
- **수용 기준:** 여러 페이지 응답 fixture에서 전체 결과 수와 현재 표시 수를 구분한다. 다음 페이지를 요청해도 기존 결과가 사라지지 않고, 중복 항목이 생기지 않는다. 마지막 페이지에는 추가 요청 버튼이 없거나 완료 상태가 표시된다.
- **코드 근거:** [API 모듈](../pages/api/index.ts) 41–47·82–88행의 검색 응답 축약, [검색 페이지](../pages/search.tsx) 48–62행의 결과 렌더링.

### UX-05 · P2 · 빈 검색·결과 없음 안내에 다음 행동 추가

- **구분:** 코드 확인 + 디자인 제안.
- **현재 문제·사용자 영향:** 빈 입력은 브라우저 `alert`로 안내하고 검증 전 입력을 지운다. 전체 결과가 없으면 `Nothing found`만 표시하며, 한 종류만 결과가 없을 때는 그 종류의 영역이 사라진다. 사용자는 무엇을 바꾸어야 할지 알기 어렵다.
- **제안:** 입력 옆에 검증 메시지를 표시하고 입력을 보존한다. 결과 없음에는 검색어를 표시하고 다른 단어·철자 확인을 안내한다. 영화/TV별 빈 상태를 구분한다.
- **수용 기준:** 공백 제출 시 포커스가 검색창에 남고 인라인 안내를 읽을 수 있다. 영화만 0건, TV만 0건, 모두 0건의 세 경우가 구분되며 각 상태에서 바로 재검색할 수 있다.
- **코드 근거:** [본문 검색창](../components/SearchBar.tsx) 12–21행, [헤더 검색창](../components/HeaderSearchBar.tsx) 16–23행, [검색 페이지](../pages/search.tsx) 60–62행, [목록 공통 컴포넌트](../components/common/Infos.tsx) 17–37행.

### UX-06 · P3 · 영화·TV 결과 필터 검토

- **구분:** 디자인 제안.
- **현재 문제·사용자 영향:** 현재 검색 화면은 영화 목록 다음 TV 목록을 항상 배치한다. TV만 찾는 사용자가 긴 영화 목록을 지나가야 할 수 있으나, 실제 검색 유형과 불편 빈도는 조사하지 않았다.
- **제안:** `전체 / 영화 / TV` 필터를 검색창 가까이에 제공하는 안을 검토한다. 결과 수를 함께 표시하고 기본값은 전체로 둔다.
- **수용 기준:** 적용하기로 결정하면 필터 전환 시 검색어가 보존되고, 선택 상태를 키보드·보조 기술로 알 수 있다. 선택 유형에 결과가 없으면 빈 상태를 표시한다. 필터 상태의 URL 저장 여부를 구현 전에 정한다.
- **코드 근거:** [검색 페이지](../pages/search.tsx) 48–59행의 영화·TV 순차 배치.

## 로딩·오류·사용자 제어

### UX-07 · P1 · 요청 하나가 느려도 다른 콘텐츠 유지

- **구분:** 코드 확인 + 브라우저 관찰 + 디자인 제안.
- **현재 문제·사용자 영향:** 홈에서는 네 요청 중 하나라도 `isFetching`이면 페이지 본문 전체를 스피너로 대체한다. 검색·트렌드에도 유사한 처리가 있다. 이미 준비된 콘텐츠를 볼 수 없고, 캐시가 있는 재조회에서도 본문이 교체될 수 있다. 배포본 모바일 검색에서는 실제 본문 전체 `LOADING` 표시를 관찰했으며 부분 지연·캐시 갱신 상황은 재현하지 않았다.
- **제안:** 최초 로딩과 백그라운드 갱신을 구분한다. 섹션별 스켈레톤·상태를 제공하고 이미 표시된 결과와 검색·기간 선택 컨트롤을 유지한다.
- **수용 기준:** 요청 하나에 지연을 주어도 완료된 다른 섹션은 표시된다. 결과 갱신 중 기존 목록과 입력·기간 컨트롤이 유지되며, 완료 시 불필요하게 포커스가 이동하지 않는다.
- **코드 근거:** [홈](../pages/index.tsx) 52–58행, [검색 페이지](../pages/search.tsx) 39–40행, [트렌드](../pages/trend.tsx) 35–36행, [컬렉션](../components/detail/Collection.tsx) 17–18행.

### UX-08 · P1 · 오류 화면에 재시도와 복귀 경로 제공

- **구분:** 코드 확인 + 브라우저 관찰 + 디자인 제안.
- **현재 문제·사용자 영향:** 오류는 `Error in ...` 텍스트만 표시한다. 앱 내부에서 사용자가 실패한 요청만 다시 시도할 명시적 버튼이나 상세 오류에서 탐색으로 돌아가는 경로가 없다. 배포본 트렌드 Day 화면에서도 영화·TV 오류와 재시도 버튼 부재를 관찰했다. 네트워크 자동 재시도의 유무와 별개인 UI 문제다.
- **제안:** 실패한 영역에 간결한 오류 설명과 `다시 시도`를 제공한다. 상세 오류에는 목록 또는 홈으로 돌아가는 링크도 둔다. 내부 오류 메시지나 API 키를 화면에 노출하지 않는다.
- **수용 기준:** 영화 조회만 실패하면 TV 결과는 유지된다. 재시도는 실패한 요청을 다시 실행하고 진행 상태를 보여 준다. 연속 실패해도 버튼·복귀 링크가 조작 가능하다.
- **코드 근거:** [메시지 공통 컴포넌트](../components/common/Message.tsx) 4–12행, [목록 오류](../components/common/Infos.tsx) 38행, [영화 상세](../pages/movies/[id].tsx) 25–30행, [TV 상세](../pages/tvs/[id].tsx) 24–29행.

### UX-09 · P2 · 404에서 사용자가 이동 시점 선택

- **구분:** 코드 확인 + 디자인 제안.
- **현재 문제·사용자 영향:** 404는 5초 뒤 자동으로 홈으로 이동하며 버튼이 없다. 안내를 읽는 중 페이지가 바뀌고 사용자가 이전 페이지로 돌아갈지 홈으로 갈지 선택하기 어렵다.
- **제안:** 자동 이동을 기본 동작에서 제거하고 `홈으로`와 `이전 페이지`를 제공한다. 자동 이동을 유지하는 별도 요구가 있다면 중지 기능도 함께 설계한다.

- **코드 근거:** [예고편](../components/detail/Trailer.tsx) 5–10·16–24행, [상세 IMDb 링크](../components/detail/index.tsx) 66–70행, [TV 상세 요청](../pages/api/index.ts) 63–70행. TV 외부 ID의 별도 조회는 [TMDB 문서](https://developer.themoviedb.org/reference/tv-series-external-ids)에 설명되어 있다.
